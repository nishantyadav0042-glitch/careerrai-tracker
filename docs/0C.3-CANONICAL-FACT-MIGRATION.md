**Read-only audit. No code, schema, migration, test or documented behaviour was
changed. Nothing proposed here is implemented.**

**Date:** 23 Aug 2026 · **Base:** `main` @ `f3a5063` · **Companion:**

## 0. What this audit found, in one paragraph

The predicates are already single-authority. The **facts are not.** `isCovered()`
is imported at 18 sites and `studyDayString()` at 52 — that work is done. What no
module owns is the *count*: every consumer that wants "how much syllabus is
covered" runs its own `.filter(…).length` over its own universe, and the four
universes in play (all 46 topics · `topicMemory` · rows that exist in
`topic_coverage` · the onboarding JSONB snapshot) give four different denominators
for the same sentence. The same shape repeats on the North Star: **six producers
of `logged_days_last_7`, five of which read an eight-day window and render it as
"N/7 days logged."** That is not a style problem — `weekly-diagnosis.ts` can
literally print *"Studied 8 of 7 days."*

Two things stop this being a clean migration, and both need a founder ruling
before any code moves: **fact 7 is contradicted by the shipped contract**, and
the two biggest metrics on the mandate's own high-risk list (`study_duration`,
`weakest_section`) have unresolved semantics that predate 0C.3.

## 3. Semantic differences — how each implementation actually differs

The mandate asked not to report "20 files." These are the differences that change
the number on screen.

### 3.1 Coverage — four universes, one sentence

| Universe | Where | What "covered" is measured against |
|---|---|---|
| All 46 `TOPIC_METADATA` topics, missing rows defaulted `not_started` | `api/blueprint:105`, `student/tracker:168` | the true syllabus |
| `topicMemory` (46 + derived revision state) | `daily-insight:235`, `buddy-briefing:63`, `sales-conversion:86` | same size today; diverges the day `computeTopicMemory` filters |
| Rows present in `topic_coverage` | `components/buddy/cockpit.tsx:80` | **a student with 10 rows has a 10-topic syllabus.** The mentor's "done" count and the student's are computed against different denominators |
| `profiles.topic_matrix` JSONB | `student-brief.ts:82` | the onboarding snapshot — a *declaration*, not coverage |

The cockpit case is the one to look at first: `cockpit.tsx:80` is the mentor's
view of the same student whose app is rendering `blueprint:105`, and the file's
own neighbouring comment says the mentor "needs to see the same number the
student's app shows." For the syllabus hours it does. For the covered count it
does not.

`student-brief.ts` is not a bug — it is a **different fact** answering "what did
the student say at signup," per `canonical.ts`'s `selfReportedDeclaration`. It
needs its own key, not a migration.

### 3.2 The seven-versus-eight day window

Constitution Article 1 defines `trailing_7_days` as `[today−6 … today]` —
"seven, never eight." Five producers compute `today − 7` and then filter
`.gte(that_date)`, which is **eight inclusive days**:

```
weekly-diagnosis.ts:30      weekAgo = now − 7d   →  .gte('report_date', weekAgo)
                    :42     daysStudied = new Set(report_date).size
                    :130    `Studied ${daysStudied} of 7 days`
```

`daysStudied` is bounded by 8. The same arithmetic drives `api/weekly-signal:62`,
`api/feedback-draft:38`, `api/chat/draft:57`, and
`buddy/(dashboard)/students/[id]:66` — all four of which render the result as
`"N/7 days logged"`, and the last of which raises a mentor flag from it.
`lib/analytics.ts:134` inherits the window from four callers that all pass `−7`.

Only `prep-memory-data.ts:89` uses `addDays(today, −6)` — and that one reads a
**different table**.

I have not queried production to count how many students currently display an
8. The arithmetic is certain; the live incidence is not, and I am not claiming it.

### 3.3 `daily_reports` vs `routine_task_completions`

`prep-memory-data.ts` computes `last7.daysStudied` from `buildCompletionRecords`,
i.e. `routine_task_completions`. Per `facts/canonical.ts` those are two different
canonical questions — `dailyLogState` ("did they submit a log?") versus
`observedBehaviour` ("what did they tick?") — and 0B's header says explicitly that
they are allowed to disagree and must never be merged.

`admin/leads/[id]/page.tsx:169` assigns that value to a field named
`loggedDaysLast7`. An operator reading that row is told "days logged" and shown
"days ticked." A student who logs by hand without ticking counts in one and not
the other. This is a naming defect on an operator surface, not a calculation
defect — the fix is a second key and a rename, not a repoint.

### 3.4 Formula duplication that agrees — for now

`api/blueprint:109` and `student/tracker:135` are the byte-identical line
`notStartedCount + learningCount`. `daily-insight:236` computes the same quantity
subtractively as `topicMemory.length − finished`. All three agree **only because
the ladder partitions into exactly {not_started, learning} ∪ COVERED_STATUSES**.
The day a sixth status is added — the exact scenario `coverage-status.ts`'s header
was written about — the additive pair and the subtractive one diverge silently.

### 3.5 The one live wrong answer

`student/onboarding/screens/screen-topic-coverage.tsx:315,322,343` still writes
`m.status === 'practicing' || m.status === 'revising'` — the inline triple minus
`exam_ready`. It is the same defect `coverage-status.ts` documents as the
eleventh implementation, `prep-insight-engine`'s `isFinished`, which was fixed.
It is latent for the same reason that one was: `exam_ready` cannot be
self-assigned at onboarding. Latent is not the same as safe, and it is three
lines.

## 6. Guard plan

| Guard | Enforces | Feasible today? |
|---|---|---|
| A — one authority | each fact key has exactly one `FactDef` | yes |
| B — no consumer-side calculation | no `.filter(isCovered).length` outside `facts/` | yes, once M3/M5 exist |
| C — no duplicate formula | AST-shape match on the remaining/coverage formulas | yes |
| D — canonical time | day keys via `studyDayString()`; **and window arithmetic via one helper** | the second half is the real work — see below |
| E — canonical plan | `resolveFocusSections()` is the only weakest-section resolver | blocked on §8 |
| F — no UNKNOWN → value | no `?? 'DILR'` outside `focus-sections.ts` | blocked on §8 |
| G — same-moment invariant | two renderers of one fact, one input, one output | yes |
| H — no dead authority | every `FactDef` has ≥1 consumer | yes |
| I — no orphan consumer | extend `orphan-surfaces.guard.test.ts` | yes |
| J — duplicate query detection | no second `.from('daily_reports')` 7-day window outside `facts/` | yes |

**Guard D, stated accurately.** `study-day.ts` chose 05:30 IST *because* it is
00:00 UTC, so `toISOString().slice(0,10)` and `studyDayString()` return the same
string always — the alternatives were made to collapse into the authority rather
than be policed. Only 2 files construct a day key another way, and neither is on a
fact path. **The divergence is entirely in window arithmetic** (`−7` vs `−6`), which
no authority owns. Guard D should therefore pin the *window*, not the *day key* —
pinning the day key would be a guard that passes because the problem is elsewhere.

This is the fifth time in this workstream a guard risked encoding characters
instead of the idea. Recording it here so the mistake is not made a sixth time.

## 7. Consumer behaviour that would materially change — STOP CONDITIONS

The mandate says to stop and ask before any migration changes what a consumer
shows. Three would.

1. **M1 changes six student- and mentor-facing numbers.** Correcting 8 days to 7
   can only lower a count. A student on 6/7 today may read 5/7 tomorrow with no
   behaviour change on their part, and
   `buddy/(dashboard)/students/[id]:70` fires its mentor flag at `< 3` — some
   students will newly trip it. *Question: ship the correction silently, or with a
   one-time "we fixed how this was counted" line?*

2. **M3 changes the mentor cockpit's denominator.** Today `cockpit.tsx:80` counts
   over rows that exist; over all 46 the count is the same but the *proportion*
   drops sharply for a student who never completed the onboarding grid. *Question:
   should the mentor see coverage against the full syllabus (consistent with the
   student's app) or against what the student has actually engaged with?* I read
   the file's own comment as arguing for the former, but this is a mentor-product
   decision.

3. **D4 changes three onboarding analytics counters.** Believed to be a no-op
   because `exam_ready` is evidence-earned and cannot be self-assigned. I did not
   verify against production that no onboarding row holds `exam_ready`.

## 11. Method

Every file cited was opened and read; nothing is classified from a grep line
alone. `daily_reports`' `UNIQUE (student_id, report_date)` was verified in
`001_initial_schema.sql:45` — which is why row-count and distinct-date producers
are recorded as equivalent rather than as a difference. No production queries were
run for this pass; every quantitative claim above is either a code fact or is
explicitly marked unverified. The `study_duration` consumer map is cited from the
18 Aug G4 audit and was not re-derived, though the NaN hazard it recorded (A5) is
noted as since fixed — `analytics.ts` now uses `avgOrNull` and `durationIsUnknown`.
