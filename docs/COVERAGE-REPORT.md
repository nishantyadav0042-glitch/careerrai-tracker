## How to read this

**Red does not mean broken. Red means nothing has proven it correct.**
That distinction is the whole point: a wrong number can be fixed, an unknown
one cannot be managed.

A file is **GREEN** only if something independent proves its numbers — a unit
test over its logic, or a reconstruction from raw database rows recorded in the
audit trail. Assertion does not count. That is why 3% is green after two full
days of audit work: almost everything verified so far was verified by hand, and
hand-verification does not scale to 331 files.

**YELLOW** computes or displays a number but does not persist anything, so a
defect there is contained to one screen.

**RED** reads or writes business data with no independent verification.

**EXCLUDED** cannot affect business data. Every exclusion carries a reason in
the script (`EXCLUSIONS`), not a blanket skip.

## The 128

The single most important number in this report is not 82%. It is **128 files
that mutate the database with nothing proving they mutate it correctly.**
Those are the files that can silently corrupt the record that the whole product
is built on — a streak, a coverage status, a payment, a subscription.

Everything else in this report is a reporting risk. Those 128 are a data risk.

## Unclassified

47 business-data files match no known feature — account deletion, calendar and
meetings, lead capture, client errors, the coach line, engagement, the Expedify
CRM webhooks, feedback drafts. This is itself a finding: they are real
subsystems that nobody has named as a feature, which is how a subsystem ends up
with no owner, no dashboard and no tests.

## What would move this

Hand-verification got 10 files to green in two days. At that rate 331 files is
months. The only route to green at this scale is to make verification
mechanical:

1. **Invariant tests over the database**, not over files. One test proving
   "every streak in streak_data is reproducible from daily_reports" covers
   every file that writes a streak, whatever it is called and wherever it lives.
2. **Event-contract tests.** One test proving every `track()` name is in the
   registry and every registry event is emitted somewhere covers the whole
   telemetry surface.
3. **Reconciliation tests per business object** — student, notification, log,
   payment, subscription — comparing raw rows to whatever the API reports.

Those three cover most of the 331 without visiting them individually. Visiting
them individually is the approach that produced 3%.

## Re-running

```bash
node scripts/coverage-audit.mjs          # this report
node scripts/coverage-audit.mjs --red    # just the unverified business files
node scripts/coverage-audit.mjs --json   # machine-readable
```

The verified list lives in `VERIFIED` inside the script. Adding a file there
without adding the test or the reconstruction that justifies it is the one way
to make this report lie.
