## 3. Supabase

- **Production project:** `careerrai-tracker`, project ref `pobhpszlsozeonejtzqy`, region `ap-southeast-1`, Postgres 17.6.1, status `ACTIVE_HEALTHY`.
- **No keys, passwords, or secrets are reproduced anywhere in this report.**
- **Schema:** 84 tables in the `public` schema, every single one with **`rls_enabled: true`** — no exceptions found in this scan. A representative sample of table comments already documents intent precisely where it matters (e.g. `video_sessions`: "Writes are SERVER-ONLY... No RLS write policy exists by design"; `google_oauth_tokens`: "Sensitive... Server-side (service role) writes only; owner-only SELECT via RLS"). This reads as a genuinely security-conscious schema, not an afterthought.
- **Extensions installed:** `btree_gist`, **`pg_cron`**, `pg_net`, `pg_stat_statements`, `pgcrypto`, `plpgsql`, `supabase_vault`, `uuid-ossp`.
- **`pg_cron` is active — checked what it actually runs**, since a second scheduling layer at the database level would be exactly the kind of hidden competing system this audit needs to catch: only **2 jobs**, both scoped to demo/QA housekeeping — `refresh_buddy_demo_account()` and `refresh_review_account_logs()`, both daily at 19:05 UTC. **Neither touches real student data or the study-plan/notification pipeline.** All real scheduled work (35 cron entries) lives in `vercel.json`, triggered by Vercel Cron hitting `/api/cron/*` routes, gated by `CRON_SECRET`. No competing scheduler found.
- **Database constraints preventing duplicate records — real and version-controlled** (`supabase/migrations/20260814_plan_uniqueness.sql`, quoting its own header): *"There must never be two competing authoritative study plans... student_id + plan_date must resolve to exactly ONE authoritative plan."* Three unique indexes back this:
  - `daily_routines_student_id_routine_date_key UNIQUE (student_id, routine_date)` — one plan per student per day.
  - `routine_task_completions_student_date_task_key UNIQUE (student_id, routine_date, task_id)` — a task can't be double-completed.
  - `topic_coverage_student_section_topic_key UNIQUE (student_id, section, topic)` — one coverage row per topic per student (this is also what the prior audit's `onConflict: 'student_id,section,topic'` upserts depend on to behave as upserts rather than silently multiplying rows).
- **Authentication:** Supabase Auth. Verified directly: `auth.users` count is **422**, `profiles` count is **422** — an exact 1:1 match, no orphaned rows either direction. Every server route observed in this and the prior two audits calls `supabase.auth.getUser()` via `@/lib/supabase/server`; there is no separate/custom auth system.
- **Single Supabase project — confirmed, not inferred.** `list_projects` for this account returns exactly one project. There is no separate staging/dev Supabase instance — **development and production share the same database.** This is a real operational fact worth being deliberate about with a second agent: there is no safety net of "break the dev database instead" — every `execute_sql`/migration call, from any agent, hits the same data queried throughout this whole investigation.
- **Production users/data confirmed present, with real numbers** (all queried live, this session): 412 students, 422 total profiles (incl. buddies/admins), 19,255 `topic_coverage` rows across 364 students, 40,444 `notifications` rows, 71,173 `student_events` rows, 34,432 `perf_events` rows. This is a live, populated production system, not a shell.

## 5. ChatGPT/Codex Handoff

- **Can Codex work on the existing GitHub repo?** Yes, directly — it's public (Section 1), so read access requires no grant at all. Write access (pushing branches, opening PRs) requires a GitHub credential (a personal access token or GitHub App install) scoped to this repo, separate from whatever this Claude Code session uses.
- **What access would it need, minimally?** Repo read/write (ideally scoped to opening PRs, not direct pushes to `main` — see the recommendation below) for code work; it does **not** need Vercel or Supabase access to write code, only if you want it to independently verify deploys or query production data the way this session's audits have.
- **Does anything need to be migrated?** No. There is one GitHub repo, one Vercel project, one Supabase project (Section 3) — adding a second coding agent does not require duplicating any of them. "Migration" would only become relevant if you wanted Codex to work in an isolated environment with its own database, which is explicitly the opposite of what you asked for.
- **Does Vercel need to be reconnected?** No. Vercel deploys from `main` on push, regardless of which human or agent authored the push. Codex pushing (directly or via a merged PR) to `main` triggers the same pipeline this session's pushes do.
- **Does Supabase need to be reconnected?** No, for the same reason — Supabase is addressed by connection string/URL/keys already configured wherever the app runs (Vercel's env vars) and wherever an agent's own MCP/tooling points. Codex would need its OWN set of Supabase credentials configured in whatever environment it runs (its sandbox, or a local machine) — it doesn't share this session's MCP connection, but it doesn't need Vercel or Supabase to be "reconnected" to the project either.
- **Does existing production data remain untouched by adding Codex?** Adding Codex as an agent, by itself, touches nothing. Whether production data stays untouched depends entirely on what commands you or Codex actually run against it — same as this session, per Section 4's finding that there is no technical barrier here beyond process discipline. If Codex is given a Supabase service-role key with the same reach this session's MCP connection has, it has the same blast radius this session has.
- **What permissions should NOT be given to Codex initially:**
  - Direct push access to `main` — recommend PR-only, so a human (or this session, reviewing) sees the diff before it can deploy, closing the exact gap Section 4 flagged for this session's own current access.
  - The Supabase **service role key** (full read/write, RLS-bypassing) — if Codex needs any database access at all, the anon/publishable key plus RLS is the safer default; service-role access should be granted deliberately and narrowly, not by default.
  - Vercel project write access (env var edits, domain changes, deployment protection settings) — no coding task requires this, and Section 2 already found deploys work correctly from GitHub pushes alone.
  - Any of the third-party secrets enumerated in Section 2 (Razorpay, Gemini, Expedify, Resend, Google OAuth) — a code-writing agent needs to know these env vars *exist* and where they're read (already fully mapped in Section 2), not their values.
- **The safest way for Claude and Codex to work on the same project, given everything above:**
  1. Both agents work from `main` (or fresh feature branches off it) via GitHub, never in place of each other's uncommitted work — the same "check `git status` before anything destructive" discipline this session already follows.
  2. Route ALL merges to `main` through a PR, for both agents — this is the single highest-leverage change, since it converts today's "direct push, hope nothing collides" model (Section 4's finding) into a reviewed one, for both agents equally.
  3. Keep the Supabase MCP-equivalent connection **read-only by default** for Codex, upgrading to write only for a specific, explicitly-approved task — mirroring how this session's own instructions already require explicit confirmation before risky actions.
  4. Because this repo mixes a genuinely wide surface (Section 1's "at least five independent weakness formulas" finding, and the general pattern documented across this session's three prior audits of duplicate logic accreting when changes aren't centrally reviewed), **the single biggest risk of two agents working concurrently is exactly that pattern repeating faster** — two agents independently "fixing" the same subsystem in parallel branches is how a sixth competing implementation gets created instead of the existing five being consolidated. A shared, current architecture doc (Section 6, and the three docs already produced this session) reduces this risk more than any permission setting does.

## 6. Critical Architecture Safety

- **Canonical source of truth for the study plan:** `resolveFocusSections()` (`src/lib/focus-sections.ts:88-110`) → `buildDayPlan()` (`src/lib/plan-day.ts:117-165`) → `generateRoutine()`. Both real writers of `daily_routines` (`api/routine/today`, `lib/routine-plan.ts`, used by the cron) call through this single path. This is not a preference this report is stating — it is what the codebase's own header comments declare, with a cited founder rule on record and an incident that motivated it (three independent copies of the weakest-section rule existed before 26 Jul, consolidated after they were found to disagree in production).
- **Canonical source of truth for student progress:** `topic_coverage` (per-topic status, RLS-protected, unique-constrained per student+section+topic) plus `daily_reports`/`routine_task_completions` for what actually happened day-to-day. `student_dna`/`student_dna_history` appear to be a derived/computed summary layer on top (408 and 1,445 rows respectively) — not independently verified in this pass, flagged as **UNKNOWN in detail**, worth a dedicated read if it matters for a specific task.
- **Canonical plan-generation flow:** as above — `resolveFocusSections` → `buildDayPlan` → `generateRoutine`, backed by the `daily_routines` unique constraint.
- **Canonical replanning flow:** there is no separate "replan" engine — a syllabus-date or hours change (student-initiated via the Reschedule/hours UI, `src/lib/daily-hours.ts` and related components) simply changes the inputs (`profiles.hours_available`, `syllabus_target_date`), and the SAME canonical plan engine recomputes from them on its next run. The one dedicated automatic mechanism is `api/cron/weekly-plan-reconcile`, which writes to `plan_extensions` ("One row per student per week when the syllabus finish date moved because hours were missed" — per that table's own comment) — this is a data-tracking layer on top of the same canonical engine, not a second plan-generator.
- **Canonical cron/background-job flow:** Vercel Cron → `vercel.json`'s 35 entries → `/api/cron/*` routes, gated by `CRON_SECRET`. Confirmed to be the ONLY real scheduler — the database's `pg_cron` extension is active but limited to 2 demo-account-only jobs (Section 3), not a competing production scheduler.
- **Duplicate or competing flows that still exist today** (from this session's prior two audit documents, restated here because it's the direct answer to this question): `api/routine/add-block`'s inline `self_reported_weakest_section ?? 'DILR'` bypass of the canonical resolver; `session-credit.matchMentor()`'s raw self-report read (also bypasses the resolver); `buddy-match.ts`'s baseline-only formula (whose sole input, per this session's direct production query, is populated for **zero real students**, so this system does not currently function as designed for anyone); `student-brief.ts`'s third, independently-coded, unweighted coverage-ranking formula for the AI sales-call script; and `prep-insight-engine.ts`'s entirely separate coverage/foundation-gap engine for the one-time pre-signup Instant Insight screen, which — per the founder's own review earlier in this session — surfaced a finding contradicting a student's self-report with no acknowledgment, precisely the class of bug the 26 Jul and 14 Aug consolidations were meant to prevent elsewhere.
- **Database constraints preventing duplicates:** covered in Section 3 — three real, version-controlled unique indexes on the three tables where duplication would be most damaging.
- **Where two AI coding agents could most easily create conflicting implementations, specifically:** any of the "duplicate flows that still exist" bullet above is a live invitation — if Claude and Codex are each asked, independently and without coordination, to "fix the weakest-section inconsistency" or "fix mentor matching," the most likely failure mode based on this codebase's own documented history is exactly what already happened five times: a sixth well-intentioned, independently-coded formula, rather than a consolidation of the existing ones. The three documents already produced this session (`instant-insight-forensic-audit.md`, `weakness-truth-table.md`, `diagnostic-redesign-spec-v1.md`) exist specifically to prevent that outcome for THIS subsystem — sharing them with whichever agent picks up related work is the concrete mitigation, not a permissions setting.

## A. What must NOT be changed

- The `daily_routines`/`routine_task_completions`/`topic_coverage` unique constraints (Section 3) — these are the load-bearing guarantee behind "one plan per student per day."
- `resolveFocusSections()`'s priority order without going through the same review discipline that produced it (a founder-approved evidence hierarchy, cited in code comments) — this is not an arbitrary implementation detail to refactor casually.
- The single-Supabase-project setup should not be casually "fixed" into a dev/prod split without a deliberate decision — right now it's a known, understood risk (Section 3), not a hidden one; a rushed split could introduce new problems (data sync, migration drift) without a clear plan.
- `CRON_SECRET`-gating on every `/api/cron/*` route — do not add a new cron route without it.
- `vercel.json`'s `ignoreCommand` build-skip logic — it's doing real, correct work (confirmed live in this audit) and a careless edit could either stop legitimate deploys or start deploying on every docs commit.

## B. What ChatGPT/Codex can safely access

- The GitHub repository, read always (it's public) and write via PR (recommended, not direct push).
- The three architecture documents already produced this session, as required reading before touching the weakest-section/study-plan subsystem specifically.
- Supabase, read-only (anon key + RLS), for any task that benefits from seeing real schema/data shape — this session's own audits show RLS is consistently enforced, so a properly-scoped anon-key connection is a real safety boundary, not just a formality.
- Vercel: no direct access needed for code-writing tasks; deployment status can be checked via the public deployment URL or GitHub's own PR checks instead of granting Vercel project access.

## C. What you need to connect

- A GitHub credential for Codex scoped to this repo (PAT or GitHub App), with branch-protection on `main` requiring a PR review — this is the one actual infrastructure change implied by the recommendations above, and it's a GitHub setting, not a Vercel/Supabase one.
- If you want Codex to independently query production data (not just write code against the schema docs), a Supabase anon-key-based connection, separate from this session's service-role MCP connection.
- Nothing on the Vercel side needs connecting or reconnecting for Codex to contribute code.

## D. Recommended Claude + ChatGPT workflow

1. Both agents branch off `main`, never work directly on it.
2. Every merge to `main` goes through a PR — for both agents, not just the new one — closing the gap Section 4 found in this session's own current access.
3. Before either agent touches the study-plan/weakest-section subsystem specifically, it reads the three documents already produced this session (forensic audit → truth table → redesign spec) — this is the cheapest possible insurance against recreating the exact "five independent implementations" problem this whole investigation exists to fix.
4. Default both agents to read-only Supabase access; escalate to write access per-task, deliberately, the same way this session already asks before destructive git operations.
5. Keep ownership of "which agent is doing what" explicit and visible (a shared doc, or GitHub issues/PRs as the coordination surface) — given the single-database, single-repo, no-staging-environment reality confirmed in this report, the actual risk of two agents working simultaneously is not technical (nothing here would silently corrupt data) but coordination-shaped: two well-intentioned, uncoordinated fixes to the same subsystem is exactly the failure pattern this codebase has already paid for multiple times.
