## PART 3 — Direct Answers

**A. Student says VARC is weak, coverage says QA is structurally weaker — what should CareerRai logically conclude?**
Neither "the student is right" nor "the algorithm is right" is a logically supportable conclusion from these two signals alone, because they are not measuring the same thing. Self-report measures *felt* difficulty (which may include exam-day panic, question-type dislike, or genuine ability gaps the student has already noticed). Coverage measures *studied-vs-not*, which is activity, not ability. A structurally correct conclusion is a **compound one**: "the student's activity is more complete in VARC than in QA, AND the student still feels VARC is costing them marks" — these are not mutually exclusive, and the honest output is exactly that juxtaposition, not a forced pick between them. The codebase already has a partial answer to a *related* question (self-report vs. baseline vs. coverage, for the daily plan) in `resolveFocusSections`'s priority order — but that order was designed to pick ONE winner for scheduling purposes, not to produce an explanatory diagnosis for a student reading a screen. Those are different problems with different correct shapes of answer.

**B. Student perception vs. objective performance — which should win, and why?**
The codebase has already answered this, for the one part of the product where it matters most (the daily plan), and the reasoning is on record: `mock-informed-focus.ts:12` — "measured evidence beats remembered feeling" — but only when that evidence is COMPLETE, RECENT (≤45 days), and DECISIVE (≥3pt gap). Below that bar, self-report wins by default, not because perception is trusted equally, but because the alternative (a stale, incomplete, or marginal mock) is worse evidence than an honest guess. This is a defensible, already-implemented, already-founder-approved hierarchy: **performance > perception > historical baseline > raw coverage > hardcoded default**, with performance required to clear a real evidentiary bar before it's allowed to override. Nothing in this audit's findings contradicts that hierarchy — the finding is that it is applied in exactly one place (`resolveFocusSections`) and nowhere else in the product that also makes weakness-shaped claims.

**C. With no performance data, how much can topic coverage legitimately claim?**
Coverage can legitimately claim facts about *itself*: what has been tapped, what hasn't, how that compares within a section. It cannot legitimately claim ability, marks, or exam performance — no code path in this product currently connects `topic_coverage.status` to any scored outcome. The prior audit's Part J already established this; this document's addition is that THREE different formulas make coverage-based claims with three different weightings (`prep-insight-engine`'s editorially-weighted gap, `section-weakness.ts`'s differently-weighted gap, `student-brief.ts`'s unweighted %-covered) — so even within "what can coverage legitimately claim," the product doesn't have one internally consistent answer to "how weak, exactly."

**D. Does "untouched prerequisite" prove the student is weak in the parent topic?**
No. It proves a **sequencing risk** — the student is spending time on a topic whose stated foundation (per `TOPIC_METADATA`'s editorially-authored prerequisite graph, itself explicitly disclaimed as "NOT measured data," `topics-constants.ts:121-126`) is incomplete. That is a real, structurally sound thing to flag. It is not evidence the student is performing poorly on the parent topic's actual exam questions — no performance data enters `findFoundationGap` at all.

**E. Does "learning" status prove weakness?**
No, and the current formulas treat it inconsistently even amongst themselves: `prep-insight-engine.ts`'s `gap` counts `learning` topics at half the weight of `untouched` ones (`weightLearning`, single-counted, vs. `weightUntouched`, double-counted); `section-weakness.ts`'s `weakestFromCoverage` does the same 2:1 ratio but on raw counts instead of weightage. Both treat "actively being learned right now" as evidence of weakness rather than evidence of engagement — a defensible modeling choice for "how much work remains," but not the same claim as "the student is weak here," and the copy on the Instant Insight screen doesn't distinguish the two.

**F. Can CareerRai currently claim a foundation gap is CAUSING poor performance, or is that causal language unsupported?**
Unsupported, as stated. This was already flagged precisely in the prior audit (Part G): `detectFoundation`'s copy — "That's why the hard questions feel random — you're above your own base" — asserts a causal link between an unmet prerequisite and a *felt experience during exam questions*, and no question-level or mock-level performance data is read anywhere in `prep-insight-engine.ts` to substantiate it. The underlying graph fact (topic X's stated prerequisite Y is untouched) is real and correctly computed; the causal leap from that fact to "this is why questions feel random" is not evidenced by anything in the input data.

**G. Genuinely useful evidence vs. legacy/dead/duplicated representations?**

*Genuinely useful, as currently built:*
- `mock_debriefs` / `mockInformedFocus()` — real performance data, real evidentiary gating, real disclosure rule. The strongest asset in the whole system.
- `self_reported_weakest_section` — real signal, correctly ranked below performance, used across five+ real features.
- `self_reported_weak_topic` — finer-grained, genuinely additive.
- `resolveFocusSections()` — not a data source but a genuinely well-reasoned combining policy, with founder-approved priority ordering and a documented incident (the "0 students diverging but latent" near-miss) that justifies its own existence.

*Dead:*
- `section_elo` — schema-only, zero code references.
- `self_reported_strongest_section` — read by the resolver, written by nothing.

*Orphaned (live read, no confirmed write path in this repo):*
- `baseline_varc/dilr/qa`, `baseline_locked`, `baseline_mocks_taken`, `starting_percentile` — all funnel through one route (`api/profiles/baseline/route.ts`) with no client caller found anywhere in `src/`. This is the single biggest open question in this whole document: if these are genuinely empty in production, `weakestFromBaseline` and `buddy-match.weakestSection` are dead weight dressed as rank-3 signals; if they're populated out-of-band, they're a real, currently-invisible-to-this-audit data source.

*Duplicated:*
- Three independently-coded coverage-ranking formulas (`prep-insight-engine.ts` weighted-by-editorial-weightage, `section-weakness.ts` weighted-2:1-unweighted-by-topic-value, `student-brief.ts` simple %-covered) — same underlying question, three different arithmetic answers, for three different audiences (Instant Insight, real plan's last-resort fallback, sales call script).
- Two independently-coded "which section, from raw self-report, with a hardcoded DILR floor" bypasses (`routine/add-block`, and effectively `session-credit.matchMentor`'s raw read) that sit OUTSIDE the canonical resolver the rest of the product converged on.

**H. Which system should become canonical, if any?**
This document does not decide that — it's explicitly out of scope per your instruction. What the evidence supports saying: **`resolveFocusSections()` is already the closest thing to a canonical pattern in the codebase**, not because of its specific formula, but because of the *properties* it has that nothing else in this table does — a single documented priority order, a founder-approved evidentiary hierarchy (performance beats perception beats history beats raw coverage), a disclosure rule (never silently override), and a citable incident that justified consolidating three prior copies into one. Whatever the redesign eventually decides, those four properties — not this specific formula — are what's missing everywhere else this table found a competing answer.
